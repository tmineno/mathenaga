# ADR-004: 受け入れテストは固定したテスト用原稿で確かめ、仕様に今の原稿から決まる値を書かない

## Context

受け入れテストは、`content/` の原稿(基準原稿)をそのまま入力にしている。仕様の受け入れテストには、その原稿から決まる値が書いてある。駅の数、乗換駅や分野の範囲の駅の並び、表示番号、式番号、通知の件数、地の文の中の文字の位置である。原稿を書くと、これらの値が変わる。そのたびに、仕様とテストを同じコミットで数え直してきた。

- 2026-10-25 から 2026-11-02 までに、原稿のコミット 7 つが数え直しを伴った。第0章に Z03 を足したときは、原稿のほかに仕様 3 ファイルとテスト 2 ファイルを直した。
- 仕様の受け入れテストの節には、駅の数・件数・表示番号を含む行が 95 行ほどある(grep での目安)。
- [site.md](../spec/site.md) の受け入れテスト 23〜26 は、第3章の地の文の中の文字の位置(`[3:A04:18:30]` など)を確かめる。第3章の文章を校正するだけで、このテストが変わる。
- [content/lines.yml](../../content/lines.yml) は、受け入れテストが路線を足すのに使うので、第14章と第15章を空けている。テストの都合が、原稿の章の番号を縛っている。

数式の個数と式番号の範囲は、すでに期待値を手で書かず、テストがビルドとは別の単純な数え方で原稿から数えている。ただし、この方法が使えるのは個数だけである。乗換駅の並びや路線図の配置の期待値を同じ方法で出すには、ビルドと同じ規則をテストにもう一度書くことになる。

## Decision

- 受け入れテストの入力を2つに分ける。
  - **テスト用原稿**(`tests/fixtures/content/`):この ADR を採ったときの `content/` を写し、固定したもの。具体的な値を確かめるテストは、すべてこれを入力にする。テスト用原稿を変えるのはテストの意図を変えるときだけで、それは人間が決める。原稿を書いても、テスト用原稿は変わらない。
  - **今の原稿**(`content/`):値を書かない不変条件だけを確かめる(下の表)。
- 仕様の受け入れテストに書く値は、テスト用原稿から決まる値だけにする。今の原稿から決まる値は、仕様にもテストにも書かない。
- 不変条件の確かめに期待値が要るときは、テストが、ビルドとは別の単純な読み方で原稿から計算する(今の数式の数え方と同じ)。計算した値は、どのファイルにも書き込まない。
- 仕様や README で今の原稿の量に触れるときは、値を書かずに述べる(「書いた章のすべて」)。
- テスト用原稿は、写したものをそのまま使う。削って小さくするのは、テストの意図を変えずに済む範囲に限る。
- 新しい書き方(ブロック・属性・記法)をツールに足すときは、それを使う例を、ツールの変更と同じコミットでテスト用原稿に足す。

### 今の原稿で確かめる不変条件

表にあるものは、今の原稿とテスト用原稿の両方で確かめる。表にないものは、テスト用原稿だけで確かめる。

| 仕様 | 今の原稿で確かめるもの |
|---|---|
| [build.md](../spec/build.md) | 8(各章の数式の個数が、原稿・ビルド・KaTeX で一致する)、9 の前半(`defs.json` に全定義が1項目ずつ、ID の順に並ぶ)、11 の前半(各章の式番号が 1 から重複なく、原稿の式の数だけ振られる)、16(2回ビルドするとバイト単位で一致する)、21(定義と定理の番号が書いた順に振られる)、26 の前半(`?v=` がファイルの中身のハッシュと一致する)、27 の前半(応用の番号が並ぶ順に振られる) |
| [content-format.md](../spec/content-format.md) | 2 から値を除いたもの(エラーがなく、通知は N01 と N02 だけで、第0章の駅は N01 に入らない) |
| [route-map.md](../spec/route-map.md) | 6(全体の図・分野の図・全章の章ページの図で、札・駅名・印・章の札・線が重ならない)。新しく次を足す:書いた駅は全体の図にちょうど1回ずつ描かれ、未執筆の駅は全体の図にだけ描かれる。幹線の駅は読む順に並ぶ。11(目視)も今の原稿で行う |
| [site.md](../spec/site.md) | 10(幅 400px で全ページに横スクロールが出ない)、15 の前半(式番号の個数)、33 の前半(証明の詳細の個数) |

## Consequences

- 原稿を書いても、仕様とテストは変わらない。数え直しはなくなる。今の原稿でテストが落ちるのは、不変条件が崩れたとき、つまり原稿かツールに直すべきところがあるときだけになる。
- 移すときに期待値を変えないので、テストの意図は変わらず、弱まりもしない。仕様の文面は「基準原稿」を「テスト用原稿」に直すだけで、値はそのまま使える。
- `content/lines.yml` で第14章と第15章を空けておく必要がなくなる。
- 今の原稿の路線図は、配置の細かな値では確かめない。配置の規則はテスト用原稿で確かめ、今の原稿では重なりがないことと目視で確かめる。テスト用原稿にない形の路線(たとえば幹線のつなぎ方の新しい形)は、テスト用原稿に足すまで値では確かめられない。
- テスト用原稿は、時間がたつと今の原稿から離れていく。テスト用原稿の誤字や古い書き方は直さない(直すとテストの意図が動く)。
- リポジトリに原稿の写し(約 270KB、15 ファイル)が増える。リポジトリ全体を grep すると、原稿と写しの両方が見つかる。AGENTS.md の参照の確かめ方(`grep -rn "\[\[" content/`)は `content/` だけを見るので、影響はない。
- 用語「基準原稿」([README](../spec/README.md))と、AGENTS.md の「9. ビルドと確認」の2の数え直しの手順を書き直す。

## Alternatives

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| テスト用原稿を固定し、今の原稿には不変条件だけを当てる(採用) | 今の原稿の写しを固定し、値を確かめるテストをそこへ移す | 数え直しがなくなる。今の期待値をそのまま使え、テストの意図が変わらない | 写しを持つ。今の原稿の配置を値では確かめない |
| 骨組みだけの小さなテスト用原稿を新しく作る | 見出しと requires と最小限のブロックだけの原稿を、テストのために作る | 小さく、どのテストが何を確かめるかが読みやすい | 期待値をすべて作り直すことになり、その途中でテストを弱めるおそれがある |
| 仕様に placeholder を書き、ビルダか CI が値を埋める | 仕様に `{{…}}` を書き、ビルドか CI がそこへ値を代入する | 仕様の文面を手で直さずに済む | ビルダが計算した値と比べても何も確かめられない(バグがあれば、その値が仕様に入る)。埋めた結果をコミットすれば、差分は今と同じだけ出る |
| 期待値をすべてテストが原稿から計算する | 数式の数え方を、乗換駅・分野の範囲・配置にも広げる | 写しが要らない | 表示番号・分岐駅・配置の期待値を出すには、ビルドと同じ規則をテストにもう一度実装することになり、二つが同じ誤りを持ちうる |
| 今のまま数え直す(従来) | 原稿を書くたびに、仕様とテストの値を同じコミットで直す | ツールもテストも変えない | 原稿のコミットのたびに仕様が変わる。第3章を校正するだけで、文字の位置のテストが変わる |

## Exit criteria

次のどちらかが起きたら見直す。

- テスト用原稿を直すコミットが、原稿の章を書くコミットと同じくらいの頻度で出るようになった(テスト用原稿が、実質的に第二の原稿になっている)。
- 今の原稿でだけ起きる不具合(テスト用原稿にない形の路線や章で崩れる)が続けて見つかった。そのときは、その形をテスト用原稿に足すか、不変条件を増やす。
