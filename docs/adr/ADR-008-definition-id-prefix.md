# ADR-008: 定義の ID を def- で始め、駅と ID を共有しない

## Context

これまで、定義の ID を省略すると、その定義を含む駅の ID になった。駅と定義が同じ ID を共有するのは、名前空間の重複の唯一の例外だった。`[[@ID]]` に共有する ID を書くと駅の表示番号(G01 など)になり、`[[キー]]` に書くと定義になる。

この決め方では、駅と ID を共有する定義の番号(定義 6.2 など)を `[[@…]]` で差し込めない。定義のアンカー `#def-<ID>` はあるが、それを指す書き方がない。定義に別の `#ID` を付ければ番号は出るが、駅名と定義の name が同じなので、名前で探すと候補が2つになり、`[[位相空間]]` のような参照が E07 で止まる。第6章の証明の骨格で、閉集合の定義(位相空間の定義の中にある)を番号で示そうとして、この問題が出た。

2026-11-07 の原稿では、駅と ID を共有する定義が 18 個あり、その ID を書いた `[[@ID]]` が 103 件ある。どれも駅の表示番号として書かれている。

## Decision

- 定義の ID は `def-` で始める。ほかの種類の ID は、これまでどおり `def-` で始められない。
- 定義の ID を省略すると、`def-<駅ID>` になる。駅と ID を共有する例外はなくなり、駅と定義はいつも別の ID を持つ。
- 名前で探すときは、駅と、その駅の中の ID が `def-<駅ID>` の定義を1つの候補として数え、定義に解決する。駅名と定義の name が同じでも、これまでどおり曖昧にならない。
- `[[キー]]` のキーが ID に一致するときは、その ID の駅か定義に解決する。`[[cauchy-sequence]]` は駅へのリンク、`[[def-cauchy-sequence]]` は定義になる。
- 定義のアンカーは定義の ID そのもの(`#def-cauchy-sequence`)にする。アンカーの形はこれまでと同じなので、定義の URL は変わらない。
- 今の原稿とテスト用原稿の定義の `#ID`、定義を ID で指す `[[…]]` と `[[@…]]` を書き換える。今は定義のポップアップが出る `[[駅ID]]` は、`[[def-…]]` に書き換えて同じ表示を保つ。

## Consequences

- どの定義も `[[@def-…]]` で番号を差し込める。駅と ID を共有していた定義も「定義 6.2」と表示できる。
- 仕様から、駅と定義の ID の共有についての規則(名前空間の例外、省略した ID の数え方、E04 の項目)が消える。定義の ID の形は E03 で検査する。
- `[[@駅ID]]` は、これまでどおり駅の表示番号になる。103 件の参照は書き換えない。
- 定義を ID で指すときは、毎回 `def-` を書く。
- `defs.json` のキーと id は `def-` で始まる。
- 原稿の書き換えは、ほかのブランチで進んでいる章の作業と衝突しうる。マージの前に、そのブランチでも同じ書き換えを行う。

## Alternatives

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| 定義の ID を def- で始める(採用) | ID そのものに `def-` を付け、駅と ID を共有しない | 共有の例外が消え、書いた ID と参照する ID とアンカーが一致する | 今の原稿とテスト用原稿の書き換えが要る |
| 参照の書き方だけ `[[@def-<ID>]]` を足す | ID は今のまま。`[[@def-<ID>]]` のときだけ定義を指す | 原稿を書き換えない | 共有の例外が残り、原稿に書く ID と参照する ID が食い違う |
| `[[@ID]]` を定義に向け直す | 共有する ID の `[[@ID]]` を「定義 N.M」にする | 書き方が増えない | 103 件の表示が変わる。駅を指す書き方が別に要る |
| 定義に別の `#ID` を付けられるようにする | 名前で探すときに、駅と同じ name の定義を1つの候補とみなす | 書き換えが少ない | 定義のアンカーが変わる。ID が増え、名前の規則に例外が残る |

## Exit criteria

定理など、ほかの種類の ID にも接頭辞が要る問題(駅や定義と ID がぶつかる、種類を ID から読み取りたい)が出たら、接頭辞の規則をほかの種類に広げるかを検討する。
