# Feature: 原稿の形式

> **Status:** Draft · Spec-driven kickoff · 2026-11-01
> **Owner:** Taiki Mineno
> **Related:** [README](README.md)(用語)、[build.md](build.md)、[route-map.md](route-map.md)、[site.md](site.md)

## Goal

執筆者は、路線ファイル・分野ファイル・章の md の3種類(文献を引くなら、文献の一覧も)を書けば、サイト全体を作れる。ビルドは原稿の誤りを一度にすべて見つけて一覧にし、誤りのある原稿からはサイトを作らない。この文書は、これらのファイルの形式と、ビルドが検査する規則を定める。

## Non-goals

- 章の本文を分野ごとに書き分けること。分野版を書けるのはゴール・出発点・分野での応用の3つだけで、確認問題などは全分野で共通にする。
- md に HTML を直接書くこと。md の中の HTML タグは解釈せず、文字のまま表示する。
- 定義・定理への番号付け(「定義 3.1」など)。表示番号を振るのは駅・章・別行立ての式だけ。
- 式番号を個別に外すこと、1つの別行立ての中で行ごとに番号を振ること。別行立ての式には必ず番号が1つ付く。
- 複数の執筆者が分野ごとに分担すること。全分野を同じ執筆者が書く前提で形式を決めている。
- 英語版などの多言語化。
- ウェブページ・未刊行の資料を文献にすること。実在と書誌を確かめる手段がない([ADR-005](../adr/ADR-005-notes-and-references.md))。

## Inputs / Outputs

入力は `content/` の下のファイルである。出力は、ビルドの1段目が作る章グラフ([build.md](build.md))と、エラー・通知の一覧である。

### ファイル配置

```text
content/
  lines.yml                     路線ファイル
  references.yml                文献の一覧(任意。下の「参考文献」)
  references.verified.json      文献の確認の記録(`npm run refs:verify` が書く。手で書かない)
  fields/
    physics.yml                 分野ファイル(ファイル名が分野の ID)
    cs.yml
  chapters/
    03-completeness-fixed-point/  章フォルダ(接頭辞の数字が章番号、残りが章の ID)
      index.md                  章の md
      figures/                  章で使う図(任意)
        step-function.svg
```

- `content/chapters/` の下のフォルダは、すべて章フォルダとみなす。
- 章フォルダの名前は「章番号-章の ID」と書く(`03-completeness-fixed-point`)。章番号は先頭の数字を 0 以上の整数として読むので、`03` と `3` は同じ番号である。フォルダ名を章の順に並べるための 0 埋めは任意。
- 章の順序は章番号だけで決まる。章番号は飛んでもよい(0, 1, 2, 4 など)。章番号を変えても章の ID は変わらないので、URL と `[[@ID]]` はそのまま使える。
- 章フォルダの中で読むのは `index.md` と `figures/` だけで、ほかのファイルは無視する。
- 図は md から相対パスで参照する(`![階段関数](figures/step-function.svg)`)。番号とキャプションの付け方は下の「図」。

### ID

- ID は英小文字・数字・ハイフンで書く(`^[a-z0-9]+(-[a-z0-9]+)*$`)。`def-` で始まる ID は使えない(定義のアンカー `#def-<ID>` と衝突させないため)。
- 路線・分野・章・駅・定義・定理・式・図・応用・文献の ID は、サイト全体で1つの名前空間に属する。重複はエラーにする。例外は、駅と、その駅の中の定義1つが同じ ID を共有する場合だけである。
- 章の ID はフォルダ名から章番号とハイフンを除いた部分、分野の ID はファイル名(拡張子を除く)で決まる。ファイルの中に ID を書く項目はない。
- 定義の ID を省略すると、その定義を含む駅の ID になる。駅と同じ ID を持てる定義は駅ごとに1つまでで、省略した定義と、駅の ID を明示した定義の両方を数える。
- 定理の ID は省略できない。定理の ID はページ内のアンカーに使い、`[[…]]` の参照先にはならない。
- 式の ID は任意で、ページ内のアンカーと `[[@ID]]` に使う(下の「式番号」)。
- 図の ID は任意で、ページ内のアンカーと `[[@ID]]` に使う(下の「図」)。
- 応用(application)の ID は任意で、`::: application {#ID field=… title="…"}` と書く。ページ内のアンカーと `[[@ID]]` に使う。
- 文献の ID は文献の一覧(`references.yml`)に書く。章ページの参考文献の項目のアンカーと `[[@ID]]` に使う(下の「参考文献」)。
- URL とアンカーには、表示番号ではなく ID を使う。

### 前提(requires)と読む順

- 読む順は、章番号の順、章の中では駅の見出しの順である。
- requires は論理的な前提だけを表す。読む順に合わせるための requires は書かない。
- requires に書けるのは駅の ID だけで、読む順でその駅より前にある駅しか指せない。自分自身も指せない。この規則により requires は循環しないが、循環があればその一覧もエラーに含める。
- 路線上の駅の並びは読む順で決まり、requires とは関係しない。
- 1つの章は1つの路線に属する。

### 路線ファイル(lines.yml)

路線の配列である。並びは、路線図で幹線を左から置く順と、凡例の順になる。

| 項目 | 内容 | 必須 |
|---|---|---|
| id | 路線の ID | 必須 |
| code | 路線記号。英大文字1文字以上(`^[A-Z]+$`)で、路線どうしで重複できない。表示番号の頭に付く | 必須 |
| name | 路線名 | 必須 |
| color | 路線の色。`#RRGGBB` | 必須 |
| color_dark | ダークテーマで使う路線の色。`#RRGGBB`。書かなければ color を使う | 任意 |
| style | 線の種類。`solid`(実線)か `dotted`(点線)。書かなければ `solid` | 任意 |
| layout | 支線として分岐する向き。`up`・`down`・`right` のどれか。書かない路線は幹線になる。親の路線が幹線より上か下の段にあれば、向きは親の路線で決まり、この値は使わない([route-map.md](route-map.md)) | 任意 |
| planned | この路線に載る、まだ書いていない章の配列(下の「未執筆の章」) | 任意 |

- 幹線は1つ以上要る。
- 0番線は `style: dotted` にして、同じ色の本線と見分けられるようにする。

```yaml
- id: reading
  code: Z
  name: 0番線
  color: "#8790A1"
  style: dotted
- id: main
  code: M
  name: 本線
  color: "#8790A1"
- id: analysis
  code: A
  name: 解析線
  color: "#5B45B8"
  color_dark: "#AA98F2"
  layout: up
- id: geometry
  code: G
  name: 幾何線
  color: "#0F7F73"
  color_dark: "#4DC1B3"
  layout: down
```

#### 未執筆の章(planned)

まだ章フォルダを置いていない章を、路線図に予定として描くための項目である。章フォルダの仮原稿は要らない。

| 項目 | 内容 | 必須 |
|---|---|---|
| chapter | 章番号。0 以上の整数。章フォルダの章番号とも、ほかの planned の章番号とも重複できない | 必須 |
| title | 章のタイトル | 必須 |
| stations | 予定の駅名の配列。1つ以上 | 必須 |
| requires | 前提にする駅の ID の配列。路線図で、支線の分岐駅を決めるのに使う。読む順で前の駅だけを指せる | 任意 |

- 未執筆の章は、全体の路線図にだけ現れる([route-map.md](route-map.md))。章ページ・定義索引・次の章の案内・分野の範囲・参照範囲には入らない。
- 未執筆の駅には ID も表示番号もなく、`[[…]]` の参照先にならない。表示番号は書いた駅だけで振るので、途中の章を書き終えると、その後ろの駅の表示番号は変わる。
- 支線の最初の章が未執筆なら、requires に、幹線か路線ファイルでその支線より前にある支線の駅を書く。書かなければ E12 で止まる([route-map.md](route-map.md))。
- 章を書き終えたら、章フォルダを置き、planned からその章を消す。消し忘れると章番号の重複で E04 になる。

```yaml
- id: analysis
  code: A
  name: 解析線
  color: "#5B45B8"
  layout: up
  planned:
    - chapter: 10
      title: 作用素
      stations: [有界作用素, スペクトル]
```

### 分野ファイル(fields/<分野ID>.yml)

| 項目 | 内容 | 必須 |
|---|---|---|
| title | 分野名 | 必須 |
| description | 分野の入口ページに出す1〜3文の紹介文 | 必須 |
| goals | 目標の配列。1つ以上で、kind が final のものを1つ以上含む | 必須 |
| goals[].station | 目標の駅の ID | 必須 |
| goals[].kind | `final`(終着駅)または `partial`(途中下車駅) | 必須 |
| goals[].label | 路線図と入口ページに出す目標の説明 | 必須 |

- 同じ分野の goals に、同じ駅を2回書けない。
- 分野は、ファイル名(分野の ID)の文字コード順に並べる。切り替えの選択肢、トップページの一覧、折りたたんだ分野版の順、式番号の順は、この並びに従う。

```yaml
title: 理論物理
description: >
  量子力学のヒルベルト空間と、一般相対論の多様体。
  理論物理で出会う二つの空間まで、距離空間から路線を引きました。
goals:
  - station: hilbert-space
    kind: final
    label: 量子力学の状態空間
  - station: picard-lindelof
    kind: partial
    label: 微分方程式の解の存在が目的ならここまで
```

### 章の md:front matter

| 項目 | 内容 | 必須 |
|---|---|---|
| title | 章のタイトル | 必須 |
| subtitle | 副題 | 任意 |
| line | 章が属する路線の ID | 必須 |

章番号は front matter に書かない。章フォルダの名前で決まる(「ファイル配置」)。

### 章の md:本文の構成

本文は、章頭・駅・章末の3つの部分からなる。

1. **章頭**:最初の駅の見出しより前。goal と motivation のブロックと、地の文を書く。地の文は出発点の続きとして表示する。
2. **駅**:2段目の見出しから、次の駅の見出しか章末の始まりまで。駅のブロックと地の文を書く。3段目以下の見出しは、駅の中の小見出しになる。
3. **章末**:最初の review か question のブロックから最後まで。review・question・answer のブロックだけを書ける。

- 1段目の見出し(`#`)は書けない。章のタイトルは front matter に書く。
- 2段目の見出しはすべて駅で、`## 駅名 {#ID requires=…}` と書く。見出し属性には `#ID`(必須)と `requires`(任意)だけを書ける。requires はカンマ区切りで、空白を入れない(`requires=completeness,contraction`)。
- 駅名は見出しの文字列である。駅名には数式と参照(`[[…]]`)を書けない。強調などの装飾は、路線図とポップアップでは外して使う。

### 章の md:ブロック

ブロックは `::: 名前 {属性}` の行で開き、`:::` だけの行で閉じる。ブロックの中に別のブロックは書けない。

| ブロック | 要素 | 書ける場所 | 個数 | 属性 |
|---|---|---|---|---|
| `goal` | この章のゴール | 章頭 | 共通版がちょうど1つ。分野版は分野ごとに1つまで | `field` |
| `motivation` | 出発点 | 章頭 | 共通版がちょうど1つ。分野版は分野ごとに1つまで | `field` |
| `summary` | 一言でいうと(札も枠もなく、駅の最初の地の文として表示) | 駅 | 駅ごとにちょうど1つ | — |
| `why` | なぜ必要か | 駅 | 任意 | — |
| `definition` | 定義 | 駅 | 任意 | `#ID`、`name`(必須)、`en`(必須)、`aliases` |
| `theorem` | 定理 | 駅 | 任意 | `#ID`(必須)、`name`(必須) |
| `proof-sketch` | 証明の骨格 | 駅 | 定理のある駅には1つ以上必須 | — |
| `proof` | 証明の詳細(折りたたんで表示) | 駅 | 任意 | — |
| `examples` | 例と反例 | 駅 | 任意 | — |
| `drop-assumption` | 仮定を外すと | 駅 | 任意 | — |
| `pitfall` | 落とし穴 | 駅 | 任意 | — |
| `remark` | 補足(読み飛ばしてよい、段落単位の補足) | 駅 | 任意 | — |
| `application` | 分野での応用 | 駅 | 何個でも(同じ分野のものを2つ以上書いてもよい) | `#ID`(任意)、`field`(必須)、`title`(必須) |
| `review` | ふりかえり | 章末 | ちょうど1つ | — |
| `question` | 確認問題 | 章末 | 任意。1つもなければ通知 | — |
| `answer` | 確認問題の答え(折りたたんで表示) | 章末 | question の直後にちょうど1つ | — |

- 属性は `#ID`、`キー=値`、`キー="空白を含む値"` の形で書く。`aliases` はカンマ区切りで、複数の別名を書ける。
- 表にないブロック名と属性はエラーにする。
- `field` には分野の ID を書く。`field` を書けるのは goal・motivation・application だけである。
- 駅の中のブロックと地の文は、書いた順に表示する。application だけは駅の末尾にまとめる([site.md](site.md))。同じ分野の application を2つ以上書いたときは、その分野の中で書いた順に並び、読者がその分野を選ぶと最初の1つを開いて表示する。主な応用を先に書く。
- 用語は初出で日本語と英語を併記する。用語の衝突(位相 = phase と topology など)は、落とし穴(pitfall)で扱う。
- 現在地・次の章・この先の行き先はツールが作るので、書かない。

### 数式

- 行内は `$…$`、別行立ては `$$…$$` で囲む。別行立ては複数行にわたってよい。
- 本文の「$」そのものは `\$` と書く。コード(`` `…` `` と ```` ``` ```` で囲んだ部分)の中の `$` は数式にしない。
- 数式はビルド時に KaTeX で HTML にする。
- 数式を書けるのは本文・ブロックの中・リスト・表である。属性と YAML の中の `$` は文字のまま扱う。

### 式番号

- 別行立ての式には、すべてツールが式番号を振る。形は「(章番号.章の中の通し番号)」で、例は (3.1)。通し番号は 1 から、章ページに並ぶ順に振る([build.md](build.md))。
- 番号は式の位置で決まるので、式を挿入すると後ろの番号がずれる。本文には番号を直接書かず、参照の記法で書く。
- 参照する式には、閉じる `$$` の後ろに同じ行で ID を付ける。属性は `#ID` だけを書ける。

  ```markdown
  $$
  d(x_n, x^*) \le \frac{k^n}{1-k}\, d(x_1, x_0)
  $$ {#banach-error-bound}
  ```

- 1つの別行立てに付く番号は1つで、複数行の式(`aligned` など)でも同じである。
- TeX の `\tag`・`\tag*`・`\label`・`\ref`・`\eqref`・`\notag`・`\nonumber` は使えない。番号はツールが振り、参照は `[[@ID]]` で書く。
- 行内の式には番号も ID も付けない。

### 図

- 画像だけでできた段落(画像のあいだの空白と改行はよい)を、1つの図とする。画像の前後に文字がある段落の画像は、文の中の画像で、図にしない。
- 図には、ツールが図番号を振る。形は「図 章番号.章の中の通し番号」で、例は「図 3.1」。通し番号は 1 から、章ページに並ぶ順に振る([build.md](build.md))。式番号とは別に数える。
- 1つの段落に画像が2つ以上あれば、まとめて1つの図にし、画像に (a)、(b)、… を付ける。
- 画像のタイトル(`![代替テキスト](figures/x.svg "タイトル")`)をキャプションにする。代替テキストは読み上げ用の説明で、キャプションには出さない。タイトルの `$…$` は、本文と同じく行内の数式として描く(`$` そのものは `\$` と書く)。閉じていない `$`、`$$`、KaTeX が解釈できない数式、番号と参照の命令は、本文の数式と同じく E10 にする。参照(`[[…]]`)と強調は書けず、文字のまま出る。画像が2つ以上の図では、キャプションを「(a) 〈タイトル〉 (b) 〈タイトル〉」と並べる。タイトルのない画像は、キャプションに出さない。
- 図に ID を付けるときは、段落の最後の画像のすぐ後ろに `{#ID}` を書く(`![…](figures/x.svg "…"){#fig-open-set}`)。書けるのは ID だけで、ほかの属性は E02、ID の形の誤りは E03 にする。文の中の画像の後ろの `{…}` は、ただの文字である。

```markdown
![開集合 U の点のまわりの開球](figures/open-set.svg "開集合 $U$") ![開集合でない F の境目の点](figures/not-open-set.svg "開集合でない $F$"){#fig-open-set}
```

### 参照

| 書き方 | 意味 | 表示 |
|---|---|---|
| `[[キー]]` | 定義または駅を探す | 定義なら用語(触れるとポップアップ)、駅ならその駅へのリンク。キーをそのまま表示し、キーが ID のときは定義の name か駅名を表示する |
| `[[キー\|文字]]` | 同上。語形が変わるときに、表示する文字を変える | 「文字」を表示 |
| `[[@ID]]` | 駅・章・式・定理・定義・図・応用・文献の番号を差し込む | 駅なら表示番号(A02)、章なら「第3章」、式なら式番号「(3.2)」、定理なら「定理 3.4」、定義なら「定義 3.1」、図なら「図 3.1」、応用なら「応用 3.2」、文献なら文献番号「[1]」。そこへのリンクにする(文献は、同じ章ページの参考文献の項目へ) |

キーは次の順で解決する。

1. キーが定義または駅の ID と一致すれば、その ID に解決する。参照範囲は問わない。
2. キーがそれ以外の種類(路線・分野・章・定理・式・図・応用)の ID と一致すれば、E05 にする。
3. どの ID とも一致しなければ、名前で探す。探す範囲は参照範囲(その章の駅と、そこから requires をたどれる駅)である。参照範囲の駅に属する定義の name・aliases と、参照範囲の駅の駅名を、キーと完全に一致するかで比べる。
4. 同じ ID を共有する駅と定義は1つの候補として数え、定義に解決する。
5. 候補がなければ E07、2つ以上あっても E07(曖昧さ)にして、ID での指定を求める。参照範囲の外にだけ候補があるときは、その ID をエラーの中で示す。

- 交わらない路線どうしの同名の定義は衝突しない。同名の定義を後から足しても、影響はそれをたどれる章だけにとどまる。
- 章・路線・分野・定理・式・図・応用・文献の ID は `[[キー]]` の参照先にならない。章・式・図・応用・文献を指すときは `[[@ID]]` を使う。
- `[[@ID]]` に書けるのは駅・章・式・定理・定義・図・応用・文献の ID だけである。駅と ID を共有する定義の ID は駅を指し、駅の表示番号になる。参照範囲に関係なく、ほかの章の駅・式・定理・定義・図・応用も指せる。文献はどの章からも引ける。表示する文字は変えられない。
- 駅・章・式・定理・定義・図・応用の番号は、章や駅やブロックを挿入するとずれる。本文には番号を直接書かず、`[[@ID]]` で書く。
- 参照を書けるのは本文・ブロックの中・リスト・表である。駅の見出し・属性・YAML には書けない。
- 定義の本文の中の参照も、その定義がある章の範囲で解決する。
- 文字として `[[` を書くときは `\[\[` と書く。

### 注

- 文の中に `^[注の本文]` と書くと、その位置に注の印を置き、注の本文を、その注を書いた駅か節(「この章のゴール」「出発点」「ふりかえり」「確認問題」)の末尾にまとめる(表示は [site.md](site.md)、注番号は [build.md](build.md))。
- 注を書けるのは、参照を書ける場所(本文・ブロックの中・リスト・表)である。ただし definition の本文には書けない。定義は用語ポップアップと定義索引で、ほかの章のページにも出るためである。駅の見出しにも書けない(数式・参照と同じく E09)。属性・YAML・図のタイトルの中の `^[` は文字のまま扱う。
- 注の本文に書けるのは1段落の中身(文字、行内の数式、強調、コード、`[[…]]`、`[[@…]]`)だけである。別行立ての数式と注の入れ子は書けない。注の途中に空行があれば、注は閉じていないものとする。
- 注の本文は、最初の対応する `]` で閉じる。行内の数式・コード・`[[…]]` の中の `]` は数えない。文字として `]` を書くときは `\]`、本文に `^[` を書くときは `\^[` と書く。
- 段落・小見出し・表を分ける補足は、注にせず、`remark` のブロックに書く。

```markdown
自然数全体は $\mathbb{N}$ と書きます^[0 を自然数に含めるかどうかは、本によって違います。]。
```

### 参考文献

文献は、文献の一覧 `content/references.yml` に1か所で書く。一覧はなくてもよい(なければ文献はない)。一覧は文献の配列である。

| 項目 | 内容 | 必須 |
|---|---|---|
| id | 文献の ID | 必須 |
| type | `book`(本)か `article`(雑誌の論文) | 必須 |
| authors | 著者の配列。原典の表記で書く(「杉浦光夫」「Erwin Kreyszig」) | 必須 |
| title | 書名か論文の題名。原典の表記で書き、副題があれば「主題: 副題」とする | 必須 |
| edition | 版(「第2版」「3rd ed.」) | 任意 |
| publisher | 出版社 | book で必須 |
| journal | 雑誌名 | article で必須 |
| volume・issue・pages | 巻・号・ページ(文字列) | 任意(article だけ) |
| year | 発行年。4桁の整数で、isbn・doi の指す版の年 | 必須 |
| isbn | ISBN-10 か ISBN-13(ハイフンは任意)。book だけ | doi と isbn の少なくとも一方が必須 |
| doi | DOI(`10.` で始まる。`https://doi.org/` は付けない) | doi と isbn の少なくとも一方が必須 |

- 一覧に置けるのは、`npm run refs:verify` で実在を確かめた文献だけである。確かめると、確認の記録 `content/references.verified.json` に記録ができる([reference-check.md](reference-check.md))。ビルドは記録を読み、記録がない文献と、記録を取った後に項目を書き換えた文献があれば E15 で止まる。ビルドは問い合わせない。
- 書誌は、出版社や雑誌のページなど、確認に使う検索 API とは別の情報源から書く([reference-check.md](reference-check.md) の Non-goals)。
- 本文では `[[@文献ID]]` で引く。表示は「[1]」で、同じ章ページの参考文献の項目へのリンクになる。文献番号は章ごとに振り、同じ文献は章の中で同じ番号になる([build.md](build.md))。
- 引いた箇所(節・定理の番号・ページ)は地の文に書く(「証明は [[@kreyszig-fa]] の 3.4 節にあります」)。
- どこからも引かれていない文献は、N04 で知らせる。

```yaml
- id: kreyszig-fa
  type: book
  authors: [Erwin Kreyszig]
  title: Introductory Functional Analysis with Applications

  isbn: 978-0-471-50731-4
```

### 分野版

- field 属性のない goal・motivation が共通版、field 属性のあるものが分野版である。
- 共通版のゴールと出発点は必須である。分野版はどの要素でも共通版への追加として表示する(表示の規則は [site.md](site.md))。
- application には分野版しかなく、共通版はない。
- 第0章は分野に共通の章とし、分野版の goal・motivation と application を書かない。書いてもエラーにはしないが、第0章の駅は N01 の対象にしない。

### 例

`chapters/03-completeness-fixed-point/index.md`(章番号 3、章の ID は completeness-fixed-point):

```markdown
---
title: 完備性と不動点
subtitle: 逐次近似はいつ答えにたどり着くか
line: analysis
---

::: goal
逐次近似が必ず答えにたどり着くための条件を述べ、その理由を説明できる。
:::

::: goal {field=physics}
力がリプシッツ連続なら、運動方程式の解は初期条件からただ一つに決まる。
:::

::: motivation
電卓で cos を押し続けると、表示は 0.739085… に落ち着く。
:::

## コーシー列 {#cauchy-sequence requires=metric-space}

::: summary
先に進むほど、項どうしがいくらでも近づき合う点列。
:::

[[点列の収束]]を確かめるには、行き先の点を先に知っている必要がある。

::: definition {name="コーシー列" en="Cauchy sequence"}
距離空間 $(X, d)$ の点列 $(x_n)$ がコーシー列であるとは、次が成り立つことをいう。
$$\forall \varepsilon > 0,\ \exists N,\ \forall m, n \ge N: d(x_m, x_n) < \varepsilon$$
:::

## 完備性 {#completeness requires=cauchy-sequence}

::: summary
コーシー列が必ず収束する、穴のない空間。
:::

すべての [[コーシー列]] が収束するとき、空間は [[completeness|完備]] であるという。
[[@cauchy-sequence]] の例の $\mathbb{Q}$ は完備ではない。

::: application {field=physics title="関数の空間"}
区間 $[a, b]$ 上の連続関数全体 $C[a, b]$ に、二通りの距離を入れてみる。
:::

::: review
- 空間に穴があるかどうかを判定できる(完備性)。
:::
```

この例では、`[[コーシー列]]` は駅 cauchy-sequence と、その駅の定義(ID を省略したので cauchy-sequence)の両方の名前に一致する。同じ ID を共有するので1つの候補として数え、定義に解決する。`[[@cauchy-sequence]]` は A01 になる。コーシー列の定義の別行立ての式には、ID がなくても式番号 (3.1) が付く。完成した章の全体は `content/chapters/03-completeness-fixed-point/index.md` にある。

## Failure modes
